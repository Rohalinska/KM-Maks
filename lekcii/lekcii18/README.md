## Контрольні запитання

1. **Клієнт-серверна модель vs P2P:**
* **Клієнт-сервер:** чіткий поділ ролей. Центральний сервер постійно активний і надає ресурси, а клієнти надсилають до нього запити.
* **P2P (Peer-to-Peer):** усі вузли (піри) є рівноправними. Кожен пристрій виступає одночасно і клієнтом, і сервером, обмінюючись даними напряму.
2. **Послідовність викликів сокетів на TCP-сервері:**
1. `socket()` - створення сокета.
2. `bind()` - прив'язка сокета до IP-адреси та порту.
3. `listen()` - переведення сокета в режим очікування вхідних з'єднань.
4. `accept()` - прийняття клієнтського з'єднання (створюється новий сокет для сесії).
5. `recv()` / `send()` (або `read()` / `write()`) - обмін даними.
6. `close()` - закриття з'єднання.
3. **Рекурсивний vs Ітеративний DNS-запит:**
* **Рекурсивний:** клієнт просить DNS-сервер повністю вирішити ім'я. Сервер сам робить усі проміжні запити та повертає підсумкову IP-адресу.
* **Ітеративний:** сервер не шукає адресу далі сам, а повертає клієнту підказку - IP-адресу наступного (авторитетнішого) DNS-сервера.
4. **Чотири кроки DHCP (DORA):**
* **Discover:** клієнт розсилає широкомовний запит для пошуку DHCP-сервера.
* **Offer:** DHCP-сервер пропонує клієнту вільну IP-адресу та параметри.
* **Request:** клієнт повідомляє про вибір саме цієї IP-адреси.
* **Acknowledge (ACK):** сервер підтверджує оренду адреси та надсилає фінальні налаштування.
5. **Захист HTTPS поверх HTTP:**
HTTPS шифрує звичайний HTTP-трафік за допомогою протоколу **TLS (SSL)** на транспортному рівні. Це забезпечує:
* **Конфіденційність** (шифрування даних).
* **Цілісність** (захист від підміни інформації).
* **Автентифікацію** (перевірка справжності сервера через цифровий сертифікат).
6. **Чому помилка DNS виглядає як недоступність всього сервісу:**
Браузери та додатки працюють з IP-адресами на мережевому рівні. Якщо DNS не може перетворити доменне ім'я (наприклад, `site.com`) в IP-адресу, пристрій просто не знає, на який мережевий вузол відправляти пакети, хоча сам сервер може працювати бездоганно.
7. **Ітеративний резолвінг DNS та відмінності:**
* **Послідовність кроків:**
1. Запит до **Root DNS** $\rightarrow$ відповідь з IP-адресою сервера TLD-зони (наприклад, `.com`).
2. Запит до **TLD DNS** (`.com`) $\rightarrow$ відповідь з IP-адресою авторитетного сервера домену (`github.com`).
3. Запит до **Authoritative DNS** $\rightarrow$ підсумкова відповідь із цільовою A-записом (IP-адресою).
* **Різниця з погляду учасників:** Клієнт (ПК) зазвичай надсилає один *рекурсивний* запит до локального резолвера (очікує готову відповідь). Локальний резолвер, у свою чергу, виконує серію *ітеративних* запитів до кореневих, TLD та авторитетних серверів.
8. **Поновлення оренди DHCP (Lease Renewal):**
Коли збігає 50% часу оренди (таймер T1), клієнт відправляє прямий (unicast) **DHCP Request** своєму DHCP-серверу. Крок **Discover** не потрібен, бо клієнт вже має призначену IP-адресу і знає точний IP-адрес DHCP-сервера.
9. **Різниця кодів стану (401/403 та 502/503):**
* **401 (Unauthorized) vs 403 (Forbidden):** 401 означає, що користувач взагалі не пройшов автентифікацію (не залогінився). 403 означає, що користувач автентифікований, але не має прав для доступу до цього ресурсу.
* **502 (Bad Gateway) vs 503 (Service Unavailable):** 502 означає, що шлюз/проксі (наприклад, Nginx) отримав некоректну відповідь від внутрішнього бекенд-сервера. 503 означає, що сам сервер тимчасово не здатний обробити запит (через перевантаження або технічне обслуговування).

### 2. Послідовність DORA для ноутбука в Wi-Fi мережі

1. **Discover:**
* *Відправник:* Ноутбук (`0.0.0.0`)
* *Отримувач:* Broadcast (`255.255.255.255`)
* *Суть:* Ноутбук шукає доступні DHCP-сервери в новій мережі.

2. **Offer:**
* *Відправник:* DHCP-сервер (роутер)
* *Отримувач:* Ноутбук (або Broadcast)
* *Суть:* Сервер пропонує IP-адресу (наприклад, `192.168.1.105`).

3. **Request:**
* *Відправник:* Ноутбук
* *Отримувач:* Broadcast (`255.255.255.255`)
* *Суть:* Ноутбук підтверджує вибір запропонованої IP-адреси перед усіма DHCP-серверами мережі.

4. **Acknowledge (ACK):**
* *Відправник:* DHCP-сервер
* *Отримувач:* Ноутбук
* *Суть:* Сервер закріплює орендні дані, надаючи маску підмережі, основний шлюз та IP-адреси DNS.

### 3. Аналіз помилки у твердженні

* **Чому твердження некоректне:** Метод `GET` призначений виключно для безпечного зчитування (отримання) даних із сервера, а не для їх зміни чи надсилання приватних форм.
* **Основні причини:**
1. `GET` передає всі дані прямо в URL-рядку (`?login=user&pass=123`), що відкриває приватні дані в історії браузера, логах провайдерів та на екрані.
2. Метод `GET` має суворі обмеження на довжину URL-адреси.
3. Для виконання дій, які створюють новий запис у базі даних (змінюють стан сервера), стандарт HTTP вимагає використання методу **`POST`**, який передає дані у прихованій формі всередині тіла запиту (Request Body).
