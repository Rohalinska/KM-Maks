## Контрольні запитання

1. **Доставка «від вузла до вузла» vs «від процесу до процесу»:**
* *Від вузла до вузла (Node-to-Node, мережевий рівень L3):* відповідає за доставку IP-пакета між двома фізичними пристроями в мережі за їхніми IP-адресами.
* *Від процесу до процесу (Process-to-Process, транспортний рівень L4):* відповідає за доставку даних конкретній програмі (процесу) всередині пристрою за номером порту.

2. **Сокет і його компоненти:**
Сокет - це програмний кінцевий пункт (endpoint) мережевого з'єднання. Він складається з двох компонентів: **IP-адреси** та **номера порту** (наприклад, `192.168.1.15:8080`).
3. **Триетапне рукостискання TCP (3-way handshake):**
1. **SYN:** Клієнт відправляє запит на встановлення з'єднання з початковим $seq_C$.
2. **SYN-ACK:** Сервер підтверджує отримання ($ack = seq_C + 1$) та відправляє свій $seq_S$.
3. **ACK:** Клієнт підтверджує згоду ($ack = seq_S + 1$). З'єднання встановлено.

4. **Забезпечення надійності в TCP:**
* **Ковзне вікно (Sliding Window):** регулює кількість даних, яку відправник може передати без очікування підтвердження (керування потоком).
* **Повторна передача (RTO):** якщо підтвердження (`ACK`) не надійшло до закінчення таймауту, TCP повторно відправляє втрачений пакет.

5. **Повільний старт vs Уникнення перевантаження:**
* *Повільний старт (Slow Start):* експоненціально подвоює вікно перевантаження ($cwnd$) після кожного RTT для швидкого пошуку вільної смуги.
* *Уникнення перевантаження (Congestion Avoidance):* збільшує $cwnd$ лінійно (на +1 MSS за RTT) після досягнення порогу $ssthresh$, щоб не викликати втрату пакетів.

6. **Коли UDP кращий за TCP:**
У додатках реального часу (онлайн-ігри, VoIP, відеострімінг, DNS). UDP кращий, бо не має затримок на встановлення з'єднання, підтвердження та перенаправлення втрачених пакетів, забезпечуючи мінімальну затримку (latency).
7. **Відсутні поля в заголовку UDP:**
В UDP відсутні поля `Sequence Number`, `Acknowledgment Number`, `Window Size` та прапорці керування (`SYN`, `ACK`, `FIN`). Вони не потрібні, бо UDP не гарантує доставку, порядок і не керує потоком.
8. **Чому закриття TCP називають «4-way termination»:**
TCP є повнодуплексним протоколом, тому кожна сторона повинна закрити свій напрямок передачі окремо. Кожен вузол відправляє свій прапорець `FIN` і чекає на відповідний `ACK` від іншого ($2 \times 2 = 4$ кроки).
9. **Порти 6000–6111 та фільтр у Wireshark:**
* **Порти:** Системні (Well-known) порти займають діапазон 0–1023. Порти 1024–49151 належать до зареєстрованих (Registered), куди й входять 6000–6111.
* **Фільтр:** `tcp.flags.syn == 1` відбирає лише пакети з встановленим прапорцем SYN (запити та підтвердження з'єднання), відсікаючи увесь звичайний трафік.

## Домашнє завдання

### 1. Триетапне рукостискання TCP ($seq_C = 1000$, $seq_S = 2000$)

* **Пакет 1 (Клієнт $\rightarrow$ Сервер):**
* *Прапорці:* `SYN=1`, `ACK=0`
* *Поля:* `seq = 1000`, `ack = 0` (або відсутній)

* **Пакет 2 (Сервер $\rightarrow$ Клієнт):**
* *Прапорці:* `SYN=1`, `ACK=1`
* *Поля:* `seq = 2000`, `ack = 1001`

* **Пакет 3 (Клієнт $\rightarrow$ Сервер):**
* *Прапорці:* `SYN=0`, `ACK=1`
* *Поля:* `seq = 1001`, `ack = 2001`

### 2. Обґрунтування вибору TCP або UDP

* **Завантаження вебсторінки:** **TCP**. Потрібна 100% цілісність даних (HTML, CSS, JS); втрата навіть одного байта зіпсує відображення сторінки.
* **VoIP-телефонія:** **UDP**. Критична відсутність затримок звуку; втрата кількох пакетів непомітна для людського слуху, а повторне їх надсилання запізниться.
* **Онлайн-гра в реальному часі:** **UDP**. Необхідний мінімальний пінг; застарілі координати гравців повторно відправляти немає сенсу.
* **Передача файлу по FTP:** **TCP**. Необхідна повна точність; втрачений кадр зробить підсумковий файл пошкодженим.
