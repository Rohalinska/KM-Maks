## 2. Рукостискання TLS 1.3 та перевірка сертифіката

Схема рукостискання TLS 1.3 складається з 4 послідовних кроків:

1. **ClientHello:** Браузер надсилає серверу список підтримуваних версій TLS, набори шифрів (ciphersuites) та свій публічний ключ Diffie-Hellman.
2. **ServerHello + Certificate:** Сервер обирає параметри шифрування, передає свій ключ, а також надсилає свій цифровий X.509 сертифікат.
3. **Перевірка сертифіката та підтвердження:** Браузер перевіряє автентичність отриманого сертифіката. У разі успіху браузер генерує підтвердження та узгоджує спільний сеансовий ключ.
   * **Вид перевірки 1 (Відповідність домену):** Браузер перевіряє, чи співпадає адресний рядок із полем `SAN/CN` у сертифікаті.  
     *Помилка браузера при невідповідності:* `NET::ERR_CERT_COMMON_NAME_INVALID`.
   * **Вид перевірки 2 (Термін дії):** Браузер перевіряє поточну дату за полями `Not Before` та `Not After`.  
     *Помилка браузера при простроченні:* `NET::ERR_CERT_DATE_INVALID`.
   * **Вид перевірки 3 (Довіра до видавця):** Перевіряється ланцюжок підписів до корінного центру сертифікації (Root CA).  
     *Помилка при недовірі:* `NET::ERR_CERT_AUTHORITY_INVALID`.
4. **Шифрований обмін даними:** Сторони переходять на симетричне шифрування (AES-GCM / ChaCha20) і починають захищену передачу HTTP-запитів.

## 3. Аналіз сценарію атаки (Вимкнена перевірка сертифіката)

Коли користувач або розробник вимикає перевірку TLS-сертифіката (наприклад, прапорцем `verify=False` у скриптах чи загнорувавши попередження браузера «для зручності»), пристрій втрачає можливість перевіряти справжність сервера. Зловмисник у локальній мережі може легко реалізувати атаку **Man-in-the-Middle (MITM)**, підмінивши оригінальний сертифікат своїм самопідписаним. Оскільки перевірка вимкнена, клієнт беззастережно довіряє фальшивому сертифікату, перехоплює та розшифровує весь трафік. Це повністю порушує такі властивості триади CIA, як **Confidentiality (Конфіденційність)** - хакер бачить логини, паролі та сесійні токени, та **Integrity (Цілісність)** - хакер може підміняти дані у відповідях.

**Контрзаходи:**
1. **Примусова перевірка сертифікатів (Strict SSL Verification):** повна заборона вимкнення перевірки SSL/TLS у коді додатків та заблокована можливість ігнорування помилок сертифіката на рівні групових політик (GPO).
2. **Впровадження HSTS (HTTP Strict Transport Security):** відправка сервером заголовка HSTS, який примусово заставляє браузер працювати лише через HTTPS і принципово блокує можливість користувача «проігнорувати» помилку сертифіката.

## 4. Порівняння TLS і VPN

| Критерій | TLS | VPN |
| :--- | :--- | :--- |
| **Що шифрується** | Лише трафік одного конкретного TCP-з'єднання між додатком (браузером) та веб-сервером (прикладний рівень L7). | Абсолютно весь мережевий трафік пристрою (усі IP-пакети на мережевому рівні L3) від клієнта до VPN-шлюзу. |
| **Типовий сценарій використання** | Захист окремих сесій у веб-серфінгу: авторизація на сайтах, онлайн-бангінг, завантаження веб-сторінок. | Захищений віддалений доступ працівників чи студентів до внутрішньої мережі коледжу/компанії або захист всього трафіку у відкритих Wi-Fi. |

## Контрольні запитання

1. **Які поля сертифіката перевіряє браузер під час TLS-з'єднання:**  
   Браузер перевіряє доменне ім'я (Subject Alternative Name / SAN), термін дії (`Not Before` / `Not After`), підпис центру сертифікації (Root CA) та статус відкликання сертифіката (CRL / OCSP).

2. **Яку помилку покаже браузер при невідповідності домену:**  
   Браузер видасть помилку `NET::ERR_CERT_COMMON_NAME_INVALID` (або `SSL_ERROR_BAD_CERT_DOMAIN`).

3. **Чим VPN відрізняється від TLS за обсягом захищеного трафіку:**  
   TLS захищає лише один конкретний потік даних між однією програмою та одним сервером. VPN створює зашифрований тунель для абсолютно всіх програм і всіх IP-пакетів пристрою.
